Access Controls Concepts

การควบคุมการเข้าถึง — ใครเข้าได้ ใครเข้าไม่ได้ เข้าแล้วทำอะไรได้บ้าง?
อธิบายง่ายๆ เหมือนเข้าคอนโด

สมมติบริษัทแห่งหนึ่ง พนักงานฝ่ายบัญชีสามารถเปิดดูไฟล์สูตรลับของฝ่ายวิจัยได้อย่างอิสระ ไม่มีระบบตรวจว่าใครเข้ามาเมื่อไหร่ วันหนึ่งสูตรลับรั่วไหลไปถึงคู่แข่ง แต่หาคนทำผิดไม่ได้เลย เพราะไม่มีบันทึกว่าใครเปิดไฟล์ นี่คือสิ่งที่เกิดขึ้นเมื่อระบบไม่มี Access Control ที่ดี

Access Control Flow: Identification → Authentication → Authorization → Accountability

4 ขั้นตอน Access Control

Identification → Authentication → Authorization → Accountability (IAAA)
เปรียบเทียบ: เข้าคอนโดหรู
1. Identification = บอก รปภ. ว่า "ผมชื่อสมชาย ห้อง 1204" (แจ้งตัวตน)
2. Authentication = สแกนบัตรผ่านประตู (พิสูจน์ว่าเป็นตัวจริง)
3. Authorization = ลิฟท์พาไปได้แค่ชั้น 12 ไม่ใช่ชั้นอื่น (สิทธิ์ที่ได้รับ)
4. Accountability = กล้องวงจรปิดบันทึกว่าสมชายเข้ามาเวลา 18:30 (ตรวจสอบย้อนหลังได้)
  • Identification — บอกระบบว่าคุณคือใคร เช่น Username, Employee ID, Email
  • Authentication — พิสูจน์ว่าเป็นคุณจริงๆ เช่น รหัสผ่าน, ลายนิ้วมือ, OTP
  • Authorization — ระบบตรวจว่าคุณมีสิทธิ์ทำอะไรได้บ้าง เช่น อ่านได้อย่างเดียว หรือแก้ไขได้ด้วย
  • Accountability — บันทึกทุกอย่างที่คุณทำ เพื่อตรวจสอบย้อนหลังได้ (Audit Log)

Authentication Factors

Something You Know / Have / Are

การพิสูจน์ตัวตนมี 3 ปัจจัยหลัก:

เปรียบเทียบ: เปิดตู้เซฟธนาคาร
- Something You Know = รหัสตู้เซฟ (รหัสผ่าน, PIN)
- Something You Have = กุญแจตู้เซฟ (บัตร Smart Card, โทรศัพท์รับ OTP)
- Something You Are = ลายนิ้วมือเจ้าของ (Biometrics: สแกนม่านตา, ใบหน้า)
  • Knowledge Factor — สิ่งที่คุณ "รู้" — รหัสผ่าน, PIN, คำตอบ Security Question
  • Possession Factor — สิ่งที่คุณ "มี" — Smart Card, Token, โทรศัพท์
  • Inherence Factor — สิ่งที่คุณ "เป็น" — ลายนิ้วมือ, ม่านตา, เสียง, ใบหน้า

Multi-Factor Authentication (MFA)

การยืนยันตัวตนหลายปัจจัย

MFA คือการใช้ปัจจัยอย่างน้อย 2 ชนิดที่ต่างกันในการพิสูจน์ตัวตน

ทำไมต้อง MFA?
ถ้าใช้แค่รหัสผ่าน (Know) แล้วรหัสหลุด = จบ
แต่ถ้าใช้รหัสผ่าน + OTP ในมือถือ (Know + Have) แม้รหัสหลุด แฮกเกอร์ก็ยังเข้าไม่ได้ เพราะไม่มีมือถือของคุณ

สำคัญ: การใส่รหัสผ่าน + Security Question ไม่ใช่ MFA เพราะเป็น "Know + Know" (ปัจจัยเดียวกัน 2 ตัว) ต้องเป็นปัจจัยคนละชนิดถึงจะนับว่าเป็น MFA

Access Control Models

DAC / MAC / RBAC / ABAC
เปรียบเทียบ 4 แบบ:
- DAC = เจ้าของห้องแชร์กุญแจให้เพื่อนเอง (เจ้าของข้อมูลกำหนดสิทธิ์เอง)
- MAC = ค่ายทหาร ระดับ "ลับมาก" เปิดได้เฉพาะคนที่ได้รับ Clearance ระดับนั้น (ระบบกำหนด ห้ามเปลี่ยนเอง)
- RBAC = พนักงานตำแหน่ง "ผู้จัดการ" เข้าถึงข้อมูลผู้จัดการทุกคนเหมือนกัน (สิทธิ์ตามบทบาท)
- ABAC = "เข้าได้เฉพาะเวลาทำการ + จาก IP สำนักงาน + ตำแหน่ง HR" (สิทธิ์ตามหลายเงื่อนไขรวมกัน)
  • DAC (Discretionary Access Control) — เจ้าของ (Owner) กำหนดสิทธิ์เอง ยืดหยุ่นแต่เสี่ยง เช่น File sharing ใน Windows
  • MAC (Mandatory Access Control) — ระบบ/นโยบายกำหนดตายตัว ใช้ Label/Classification เช่น "Top Secret" ผู้ใช้เปลี่ยนเองไม่ได้
  • RBAC (Role-Based Access Control) — สิทธิ์ผูกกับ "Role" ไม่ใช่ตัวบุคคล เช่น Role "HR" เข้าถึงข้อมูลพนักงาน Role "Finance" เข้าถึงข้อมูลการเงิน
  • ABAC (Attribute-Based Access Control) — ยืดหยุ่นที่สุด ใช้หลาย Attribute ประกอบกัน เช่น เวลา + สถานที่ + ตำแหน่ง + ประเภทอุปกรณ์

SSO และ Federation

Single Sign-On & Federated Identity
เปรียบเทียบ:
- SSO = บัตรพนักงาน 1 ใบ เปิดได้ทุกประตูในบริษัท (Login ครั้งเดียว เข้าได้ทุกระบบภายใน)
- Federation = พาสปอร์ต 1 เล่ม ใช้เข้าได้หลายประเทศ (Login ที่องค์กรหนึ่ง แต่ใช้ได้กับองค์กรอื่นที่ตกลงกัน)
  • SSO — ผู้ใช้ Login ครั้งเดียว เข้าถึงหลายระบบได้โดยไม่ต้องใส่รหัสผ่านซ้ำ ลดความเสี่ยง Password Fatigue
  • Federation — ความร่วมมือระหว่างองค์กร ให้ผู้ใช้ขององค์กร A เข้าใช้ระบบขององค์กร B ได้ เช่น "Login with Google" บนเว็บอื่น

Privileged Access Management (PAM)

การจัดการสิทธิ์พิเศษ
เปรียบเทียบ: Master Key ของโรงแรมเปิดได้ทุกห้อง ถ้าหายหรือถูกขโมย = หายนะ
PAM คือระบบที่ดูแล Master Key พิเศษ — ใครจะใช้ต้องขออนุมัติ, มีการบันทึก Session, หมดเวลาแล้วคืนอัตโนมัติ
  • บัญชี Admin / Root / SA คือเป้าหมายหลักของแฮกเกอร์
  • PAM ช่วย: จำกัดเวลาใช้งาน, บันทึก Session, บังคับ MFA, อนุมัติก่อนใช้ (Just-In-Time Access)
  • หลักการ: ให้สิทธิ์เท่าที่จำเป็น เวลาที่จำเป็น แล้วเอาคืน

Principle of Least Privilege

หลักการให้สิทธิ์น้อยที่สุดเท่าที่จำเป็น
เปรียบเทียบ: ถ้าจ้างช่างมาซ่อมแอร์ คุณให้กุญแจแค่ห้องที่มีแอร์ ไม่ใช่ให้ Master Key ทั้งบ้าน
  • ให้ผู้ใช้เข้าถึงเฉพาะสิ่งที่จำเป็นต่อการทำงาน ไม่มากไม่น้อยกว่านั้น
  • ลดความเสียหายเมื่อบัญชีถูก Compromise — แฮกเกอร์ทำได้แค่สิ่งที่บัญชีนั้นมีสิทธิ์
  • ใช้คู่กับ Need-to-Know (เข้าถึงข้อมูลเฉพาะที่เกี่ยวข้องกับงาน)
  • ใช้คู่กับ Separation of Duties (แยกหน้าที่ เช่น คนอนุมัติจ่ายเงิน กับ คนโอนเงิน ต้องเป็นคนละคน)
